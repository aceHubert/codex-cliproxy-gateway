### 🧠 Design Intent (Why)
* **根因二因素**：① CLI 1.1.83 自动更新后服务端执行最低版本门禁（`cosyVersion` 过旧 → 403）；② CLI 1.1.83 把签名逻辑搬入内嵌 auth WASM（`qoder_auth_wasm_bg.wasm` 的 `QoderContext.prepareRequest`），`auth` 模式输出的 `Authorization: Bearer COSY.<payload>.<md5>` 信封与 1.1.65 **逐字节同构**（签名仍为 `md5([payload, key, date, body, path].join("\n"))`，离线复刻验证），但运行时信封载荷新增当前 oauth token——CLI 每次启动用 wasm `generate_runtime_auth_fields` 按**当前 token** 重铸 `encrypt_user_info`/`key`，只存在内存；`.auth/user` 落盘值绑定写盘时刻的旧 token，token 轮换后被服务端拒绝（403 code 105 Login expired）。仓库既有 `runtimeFields()` 与该信封同构，补上 token 字段并在每次凭据加载时重铸即完全对齐，无需引入 wasm。
* **取证路径**：从 1.1.83 Mach-O 提取 base64 内嵌的 auth WASM（wasm-bindgen），在 bun 中以原版胶水驱动 `generate_runtime_auth_fields`/`prepareRequest` 得到可用签名（两地区 200）；差分分析 + md5 前像穷举确认签名公式不变；随后以纯 TS（零 wasm）自产信封双地区 200 复验，证明仓库可直接复刻。CLI 本地 `catalog-v6/v7` 缓存为 QMC 私有容器（machineId-AES 猜解失败），未走逆向。
* **档位名录**：2026-11 起两地区目录 `performance` 档位更名 `fast`；档位放行已由同日 [档位放开任务](20261106-1123-qoder-open-ultimate-performance-efficient-tiers.md) 处理，本文不重复。
